## Project Overview

This repository is a The Binding of Isaac mod named "Conch's Blessing". The Steam install directory is named "Rebirth", but that directory name does not establish the supported executable/API baseline. The repository currently does not pin a minimum Repentance or Repentance+ build, so preserve existing capability checks and fallbacks unless the support policy is explicitly changed.

Runtime load order is:

1. `main.lua` defines the reloadable `ConchBlessingRequire` loader (see API And Content Sources Of Truth) and loads `scripts/conch_blessing_core.lua` through it.
2. Core hard-gates initialization on compatible StatsAPI, MiniMAPI, and StageAPI providers, installs StageAPI's MiniMAPI bridge before support libraries load, creates the IsaacScript Common-upgraded `ConchBlessing` mod, initializes SaveManager/config/MCM/HiddenItemManager, and attaches the external StatsAPI tables.
3. Core requires `scripts/rooms/init.lua` after shared managers and StatsAPI attachment. That loader owns non-item room systems and loads Appraisal Certificate's backend dispatcher, its native Death Certificate gallery, and compatibility support for existing version-9 StageAPI sessions. The later-loaded Atropos item module owns its separate native Death Certificate return-door integration.
4. Core requires `scripts/conch_blessing_items.lua`, which builds `ConchBlessing.ItemData` and immediately fills its player-facing text from `scripts/locale` through `scripts/locale/init.lua`, then requires `scripts/conch_blessing_pockets.lua` for the cards and runes (`ConchBlessing.PocketData`, see Cards And Runes); the item loader then requires `scripts/eid_language.lua`, `scripts/callback_manager.lua`, and the item behavior modules, and registers ItemData callbacks after all behavior modules have loaded but before the first game-start dispatch.
5. Core finally loads `scripts/conch_blessing_upgrade.lua` and `scripts/conch_blessing_highlight.lua`.

Item behavior usually lives under `scripts/items/collectibles`, `scripts/items/trinkets`, or `scripts/items/familiars`. `scripts/rooms/init.lua` is a narrow loader for the implemented gallery subsystem; the repository still has no generic monster/entity/stage registry or authored room-pack loader. Do not assume non-item content is handled by `ConchBlessing.ItemData`.

The mod depends on external runtime APIs:

- StatsAPI is a hard runtime dependency; without `_G.StatsAPI.stats.unifiedMultipliers`, core initialization stops.
- Magic Conch supplies the upgrade callback API used by `scripts/conch_blessing_upgrade.lua` and is a required Workshop dependency.
- Mod Config Menu and EID integrations are optional at runtime and must remain guarded when their globals or methods are unavailable.
- EID descriptions and icons are generated from item data in `scripts/conch_blessing_items.lua`, its text in `scripts/locale/<lang>.lua`, and `scripts/eid_language.lua`.
- REPENTOGON is not a blanket hard dependency, but Appraisal Certificate requires its exact post-collision evidence and reversible smelt-inventory APIs. That active must fail closed before discharge, payment, inventory mutation, or transition when those capabilities are absent or incompatible; new Appraisal sessions additionally require native dimension/transition evidence and read-only RoomConfig spawn inspection; they do not register or place rooms.
- MiniMAPI remains a whole-mod hard runtime dependency and supplies continued version-9 Appraisal's normal HUD map display; new native rooms use engine descriptors. Core requires the custom-room add/get/set, room-icon/display-data, player-position, and dimension-callback capabilities and stops initialization when they are missing or incompatible. The installed Workshop cache reports metadata 2.58 while its Lua source reports 2.59, so this project treats neither number as a proven minimum and gates only on the methods it uses.
- Legacy version-9 gallery map teleport rides MiniMAPI's own NiceJourney contract: every Appraisal MiniMAPI room registers the single `MINIMAP_TELEPORT_HANDLER` identity whose `CanTeleport`/`Teleport` resolve through `GalleryManager.canTeleportToGalleryRoom`/`teleportToGalleryRoom` (seed-scoped, per-update-frame memoized, blocked during Death Certificate detours), and in-gallery travel uses `StageAPIGalleryRooms.teleportWithinGallery` — never a native `StartRoomTransition`. NiceJourney is gated behind the user-level `MouseTeleport` option, so the manager force-enables it only while the player stands in a settled gallery room via `MinimapAPI.OverrideConfig` (runtime-only; never write the persisted `Config` value) and withdraws the override on exit and on `MC_PRE_GAME_EXIT`.
- StageAPI is a whole-mod hard runtime dependency. Before any support library, room system, or item behavior loads, core requires a fully loaded provider with Appraisal's `LevelMap`/`LevelRoom`, extra-room transition, save-restore callback, persistent-entity, custom-door, and MiniMAPI-compatibility capabilities; a missing, partial, or incompatible provider stops initialization and enters the dependency retry/reload loop. Core must ensure the StageAPI→MiniMAPI position/dimension bridge exactly once for the current provider object, including late provider reloads. Version 2.33 is the installed/tested provider, not a proven minimum: gate on the required capabilities rather than a numeric version floor unless the support policy is explicitly changed. Legacy version-9 Appraisal revalidates the virtual graph and MiniMAPI registration; new native Appraisal revalidates native graph ownership and StageAPI return-door capabilities. Both require the exact entrance and actual return door before payment or held-trinket mutation.
- Installed GoodTrip 1.2.8 is optional and remains native-floor-only. It builds a private map solely from `Level:GetRooms()`/native `RoomDescriptor` data and exposes no StageAPI/MiniMAPI room-registration or teleport callback, so legacy version-9 Appraisal rooms cannot appear in GoodTrip's own overlay without modifying or monkey-patching that provider. Do not patch GoodTrip or claim its native transition path supports Appraisal's virtual map.
- GoodTrip [Fixed] (Workshop 2916069863, source `github.com/archibate/isaacmods`) hit-tests MinimapAPI's rendered rooms but, as installed (2.2.34), only rooms with a native `Descriptor` — it stays inert inside legacy version-9 virtual rooms and needs no mod-side code. A proposed upstream change (fork `Ba-koD/isaacmods`, branch `custom-room-provider`) makes it honor MiniMAPI's `TeleportHandler` contract, which the gallery already registers; if that merges, GoodTrip [Fixed] gains gallery click-travel with zero changes here. Never add GoodTrip-specific integration code to this mod — the MiniMAPI TeleportHandler is the single integration surface.

Core subsystem map:

- `scripts/callback_manager.lua` owns callback-key to `ModCallbacks` registration.
- `scripts/template.lua` owns upgrade morph visuals before/after item conversion.
- Upgrade presentation is cosmetic: render the default Holy Light from its vanilla ANM2 as a standalone Sprite, never spawn a combat effect and rely on zero damage. Clear visual state on completion, cancellation, room change, and game exit/start. Item-specific presentation proposals remain previews until the user asks to apply them. When the user excludes a proposal, revert its catalog entry to pending and synchronize HTML labels; keep its concept preview without running that effect in either real upgrades or `conch_morph`.
- Design upgrade transitions around each item's appearance or ability. When concealment fits, let the same evolving effect gather, obscure the change, and disperse; do not add a separate opaque cover graphic or force every item through the same conceal/reveal sequence. Installed mods may inform timing and composition, but their implementation and assets remain read-only references.
- Isaac-style sprite parts are welcome inside upgrade effects (for example clock rims/hands or native halos). The prohibition on cover graphics concerns a separate image masking the conversion, not using carefully styled art. Keep the item readable through open/transparent parts and animate the effect itself.
- Kronos's applied upgrade is the turned Saturn ring: familiar snapshots fade in, orbit faster and closer while the item darkens to black, fuse into one golden ring, collapse into the item and the result slowly regains its colour (the user changed the tint from white to black on 2026-10-11; Angel's Crown keeps its white). The ring turns with the icon (the Saturn sign rotated 232° clockwise), so its near half passes above the item. The user wants upgrade presentations long enough to absorb (MattPack's generic transformation tints for ~2.8 s before morphing); do not shorten them to a quick snap. The swallowing mouth is retired.
- Companion-based upgrade visuals use snapshots from the upgrading player's own familiars. Use random illustrative stand-ins only when that player has no familiars; do not fill a short owned list with unowned ones. Freeze the visual selection for the animation and animate sprite copies without consuming or modifying live familiars.
- Animated cosmetic floor overlays must use a per-frame floor render callback, never backdrop texture preparation callbacks. Capability-check the hook; leave room backdrop, collision, water flags and gameplay state unchanged, and discard the overlay with its owning scene. The developer console viewer explicitly previews player one; a global upgrade result with no owner may resolve a familiar roster only when the run has exactly one player, never by borrowing a co-op player's roster.
- `scripts/conch_blessing_upgrade.lua` owns validated Magic Conch origin/flag mappings, callback registration, and per-pedestal conversion transactions.
- `scripts/conch_blessing_highlight.lua` owns upgrade-eligibility presentation (which pickups show the evolution preview, its range/hop lifecycle and the Magic Conch HUD pulse); `scripts/lib/upgrade_branch_preview.lua` owns the tree's layout, timing and drawing.
- `scripts/conch_blessing_config.lua` owns language/debug/spawn settings.
- `scripts/conch_blessing_mcm.lua` owns MCM UI and setting persistence; its menu text is `ui.mcm` in `scripts/locale/en.lua`.
- `scripts/locale/init.lua` owns player-facing text: it loads the pure-data `scripts/locale/<lang>.lua` files listed in `Locale.LANGUAGES` (English is the fallback), resolves icon tokens, fills ItemData's text fields, and serves `ui.*` strings through `Locale.text`, `Locale.textIn`, and `Locale.linesIn`.
- `scripts/lib/weapon_attack_tracker.lua` owns reusable direct-player weapon-trigger counting and direction resolution; item modules own and reset their own counter state.
- `scripts/lib/damage_provenance.lua` owns actual damage-source/player ownership resolution, namespaced per-proc causal-lineage marking/merging/inheritance, and exact attack-instance proc claims for damage-triggered effects.
- `scripts/rooms/stageapi_gallery_rooms.lua` owns legacy version-9 Appraisal's reusable StageAPI room definitions, deterministic virtual graph construction under the project-owned fixed negative `StageAPIGalleryRooms.MAP_DIMENSION`, stable room markers, stock-slot geometry, and exact MiniMAPI full-map synchronization.
- `scripts/rooms/gallery_manager.lua` selects exactly one backend from the saved session. `native_gallery_manager.lua` owns new version-11 native Death Certificate visits and transactions; `death_certificate_gallery_rooms.lua` adopts engine-generated descriptors, records vanilla pedestal geometry, and converts collectible stock to the frozen trinket catalog without changing room layouts. `legacy_stageapi_gallery_manager.lua` and `stageapi_gallery_rooms.lua` retain version-9 graphs, journals, provider restoration, MiniMAPI integration, and DC detours until that floor settles; they never create a new virtual graph.
- External `StatsAPI.stats` owns unified stat multipliers and the multiplier display; there is no local `scripts/lib/stats.lua`.
- `ConchBlessing` is the IsaacScript Common-upgraded mod object. `ConchBlessing.originalMod` is the raw `RegisterMod` reference retained for support-library and legacy call sites.

## API And Content Sources Of Truth

- Keep project invariants, ownership, and recurring workflows in this file. Keep API signatures, enum/XML field lists, and tool links in `ISAAC_DOCS_REFERENCE.md`; do not turn `AGENTS.md` into a copy of external API documentation.
- For an exact API call, check sources in this order: the intended game-build documentation, the exact class or callback page, related enum/XML pages, the provider's documentation/source for external APIs, and then runtime behavior.
- `https://wofsauge.github.io/IsaacDocs/rep/` currently documents the Repentance+ base API. A method appearing there does not prove that it exists on every older Repentance build this mod might still support.
- Until the repository pins a minimum game build, preserve existing guards. For a new disputed or newer-only API, either select and test an explicit target baseline in the same change or use a capability-checked fallback; if the feature cannot degrade safely, stop and make the dependency/support-policy decision explicit before implementation.
- Engine constructors may be callable tables rather than Lua functions. Test their capability through protected construction and the resulting object's required methods; a `type(Constructor) == "function"` gate can silently disable a supported API. Keep constructor failure observable through the normal error path.
- Isaac's Lua environment exposes the game's `require` without the standard `package` global. Keep module references through `require`; do not inspect `package.loaded` in runtime code. Offline module/callback tests must hide the host's `package` global from production code so a full desktop Lua standard library does not conceal sandbox failures.
- The game's `require` keeps a module for the whole session, so `luamod conch_blessing` would rerun only `main.lua` and leave the mod without callbacks. `main.lua` therefore defines the global `ConchBlessingRequire`: this mod's `scripts...` modules run through the game's `include` with a cache that lasts one load (other names such as `json` still use the game's `require`), and every runtime file that calls `require` starts with `local require = ConchBlessingRequire or require -- reloadable loader, see main.lua` (offline tests fall back to the host `require`; `tests/test_reload_loader.py` enforces the header). `include` raises on syntax and runtime errors but returns the search's `no file` list for a missing file, which the loader turns into the usual `module ... not found` error (measured 2026-10-18). Anything that outlives a reload must cope with it: provider registrations replace by name or unregister by owner before re-adding (StageAPI, MCM, Magic Conch), and a module that changes live entities (pedestal visuals, pickup locks, pulse colours) restores them on its own `MC_PRE_MOD_UNLOAD`.
- Use `https://repentogon.com/docs.html` for REPENTOGON additions. Editor autocomplete and `.luarc.json` globals are development aids, not proof that an API exists in the target runtime.
- When available, use the game installation's `../../extracted_resources/resources` as a read-only vanilla XML/ANM2/room reference and `../../tools` for the Resource Extractor and animation tools. Re-extract after game updates before relying on vanilla implementation details.
- For StatsAPI, Magic Conch, MCM, EID, StageAPI, MiniMAPI, GoodTrip, or another mod API, inspect the installed/declared provider version and preserve capability guards even when the provider itself is a hard dependency; requiring a provider does not prove every method contract. Never infer a third-party contract only from this mod's call site.
- If documentation, extracted resources, and runtime disagree, preserve compatibility with capability checks and test the intended baseline in game. Record project-wide compatibility conclusions here or in `ISAAC_DOCS_REFERENCE.md`; keep a narrow API quirk beside the affected code.

## Files To Treat Carefully

- `scripts/lib/isaacscript-common.lua` is vendored and very large. Do not edit it unless the task explicitly requires a vendor patch.
- `scripts/lib/save_manager.lua` and `scripts/lib/hidden_item_manager.lua` are shared support libraries. Prefer changing call sites first.
- `scripts/rooms/native_gallery_rooms.lua` is the retired custom-placement native backend and remains a historical reference only. Runtime Appraisal must not require it, register its custom RoomConfigs, or call its build/placement functions. New sessions use `death_certificate_gallery_rooms.lua`; continued version-9 StageAPI sessions keep their own backend until their floor settles.
- `content/items.xml`, `content/itempools.xml`, `content/entities2.xml`, `content/costumes2.xml`, `content/pocketitems.xml`, `content/gfx/ui_cardfronts.anm2`, `content/gfx/death_items.anm2`, and `content/gfx/death_items.png` are generator-owned outputs. Do not hand-edit them unless the generation workflow is intentionally being changed.
- `generate_xml.py` rebuilds `content/entities2.xml` from ItemData familiar entries (type `3`) plus the pure-data `scripts/entities/definitions.lua` catalog for non-familiar entities. The latter is shared with each owning runtime module, uses prefixed names and explicit types, and omits variants for engine allocation. It does not load entity behaviors or preserve hand-edited XML. Extend its validated schema before adding unsupported entity attributes or child elements.
- `metadata.xml` is hand-authored release metadata. Do not conflate it with generated content or change its version unless the version rules below authorize it.
- Text files are UTF-8. On Windows, explicitly read and write UTF-8 when a tool's default encoding is ambiguous; apparent mojibake can be a terminal decoding issue. Avoid broad encoding normalization or translation rewrites outside a text/encoding task.
- Kronos's absorption captions use the game's own LanaPixel font (`font/cjk/lanapixel.fnt`, Repentance+), drawn from its atlas through `resources/gfx/ui/conch_blessing_caption_glyphs.anm2` rather than the Font API so each letter can crumble into dust. `generate_caption_glyphs.py` owns `scripts/items/collectibles/kronos_caption_glyphs.lua` (each locale character's atlas rectangle, metrics, and 2x2 ink cells), built from the extracted font; regenerate it instead of hand-editing, and rerun it when locale text gains characters (`check_locale.py` fails on a caption character missing from the table). Reference the vanilla atlas by path and never ship a copy of it. Fully restart the game after anm2 changes before checking the caption render.
- Treat files under `../../extracted_resources` and other installed mods as read-only references. Never copy another mod's implementation or assets into this repository.

## Code Style

- Keep Lua changes small and local to the item or subsystem being modified.
- Treat user examples as acceptance cases, not implementation conditions. Implement the underlying gameplay event or state transition once so it applies consistently to current and future content; do not enumerate known items, protections, entities, or room cases to simulate the requested result.
- Prefer the engine's canonical semantic operation (for example real death, acquisition, spawn, or room transition) over manipulating adjacent side effects until the example appears to work. If no canonical API exists, introduce one centralized, capability-checked abstraction with a documented fallback and limitation instead of scattered special-case branches.
- Prefer existing patterns: add item definitions to `ConchBlessing.ItemData`, then register behavior through the `callbacks` table.
- Keep `ConchBlessing.ItemData` grouped in this order: collectible items (`passive` and `active`) first, familiar items second, trinkets last. Append new items to the end of their group because generated `content/items.xml` IDs follow this registry order. An existing item whose type changes keeps its registry position (Dragon became a familiar in place) so no generated collectible ID shifts under existing saves.
- Generated XML follows the registry's textual order, but runtime item scripts are loaded with `pairs`; do not make runtime initialization depend on ItemData iteration order.
- Keep one global table per item namespace, for example `ConchBlessing.dragon` or `ConchBlessing.kronos`.
- Use `local` helpers and constants inside item files. Do not add globals unless they are part of the existing `ConchBlessing.*` API.
- Use `ConchBlessing.printDebug` for optional logs and `ConchBlessing.printError` for real failures. Avoid unconditional `Isaac.ConsoleOutput` in normal paths.
- When loading a persisted debug toggle, apply the authoritative saved settings before emitting optional diagnostics. Never let unordered `pairs` iteration temporarily enable output or leak messages when the final saved `debugMode` is off; diagnostic state must not affect gameplay or persistence.
- For a condition- or currency-gated active whose registry contract is `maxcharges = 0`, successful use must still return `Discharge = false`; its own transaction decides whether the use succeeds. Keep engine use-item animation separate from a semantic room-transition animation so `ShowAnim` does not overlap the transition.

## Non-Item Content Expansion

- `scripts/rooms/init.lua` is the explicit non-item room loader. It is required by `scripts/conch_blessing_core.lua` after shared managers are ready and before ItemData behavior loads. It currently loads Appraisal's native gallery plus version-9 virtual-gallery compatibility; there is still no generic monster, entity, stage, or authored-room-pack registry.
- New room systems should register through this loader or a documented registry beneath it. Do not hide monsters, rooms, or stages inside `ConchBlessing.ItemData` merely to reuse the item callback manager.
- Prefer future behavior paths such as `scripts/entities/<category>/<key>.lua`, `scripts/rooms/<key>.lua`, and `scripts/stages/<key>.lua`. Create only the paths needed by the implemented subsystem and keep one clear Lua namespace/registry entry per content key.
- Place new runtime assets in the folder the game itself uses for that asset type, mirroring the vanilla `resources` layout: grid and door art in `resources/gfx/grid/`, item art in `resources/gfx/items/collectibles` and `resources/gfx/items/trinkets`, and so on. Do not invent a mod-named asset folder such as `resources/gfx/conch_blessing/`; the repository already follows the vanilla layout everywhere else and a parallel tree only makes runtime paths harder to predict. Avoid cross-mod collisions through the filename instead, by keeping the vanilla naming pattern and adding a distinguishing suffix (`door_02_treasureroomdoor_angel.png` beside vanilla's `door_02_treasureroomdoor.png` and `_devil.png`). Never reuse a vanilla filename unless the intent really is to replace that vanilla asset for every mod.

### Custom Entities And Monsters

- Define each custom entity's XML metadata and Lua identity from one documented source of truth. Keep the name and type/variant/subtype consistent across `entities2.xml`, Lua, and room layouts; avoid scattering unexplained numeric IDs. Prefix new XML names and runtime data keys with a Conch Blessing-specific namespace to avoid cross-mod collisions.
- Resolve custom entity IDs with `Isaac.GetEntityTypeByName` and `Isaac.GetEntityVariantByName` after XML is loaded, cache the results, and call `ConchBlessing.printError` and skip registration if lookup returns an invalid value.
- `content/entities2.xml` declares entity identity, physics, health/tags, and its `anm2path`; the ANM2 and spritesheets are runtime assets under `resources/gfx`. With the current root `anm2root="gfx/"`, entity `anm2path` values are relative to `resources/gfx`, and ANM2 spritesheet paths are relative to the ANM2/runtime resource rules.
- Register NPC callbacks when the entity subsystem loads, not through the delayed ItemData callback pass. Use the callback's supported type parameter, then return early on variant and subtype before doing AI, room scans, target selection, or rendering work.
- Model AI as explicit semantic states. Prefer `Sprite:IsEventTriggered`, `Sprite:IsFinished`, pathfinding/target state, and collision events over hardcoded animation frame numbers or global frame counts.
- Keep transient entity state in `Entity:GetData()` under a sufficiently unique key such as `__ConchBlessing...`, or in a room-scoped runtime table. `GetData()` is shared by every mod. Persist only serializable state that must survive a transition through SaveManager, and clear cached entity references on removal, room change, new level, game exit, and mod unload as applicable.
- Use seeded entity/room RNG for attacks, drops, and room-authored random choices. Prefer `Game():Spawn` with a deterministic nonzero seed when spawn identity matters. Test friendly/charmed/frozen states and multiplayer targeting when the entity can interact with them.
- Treat kill, completed NPC death, entity removal, and room-unload cleanup as different lifecycle events. `MC_POST_ENTITY_REMOVE` alone is not proof that an entity died.

### Rooms, Room Packs, And Stages

- Distinguish runtime room behavior (`Room`, `Level`, `RoomDescriptor`, callbacks) from authored room layouts (`.stb`). Create Repentance-compatible layouts with Basement Renovator or another verified compatible editor; do not hand-edit binary STB files.
- Vanilla-pool room packs belong under `content/rooms` and must use the stage filenames/formats expected by the game/editor. Verify stage, room type, shape, doors, difficulty/weight, and custom entity IDs against extracted vanilla rooms before committing. `resources/rooms` replaces vanilla room sets and is not the default additive path.
- Use `MC_PRE_ROOM_ENTITY_SPAWN` only for layout-spawn substitution, `MC_POST_NEW_ROOM` for room-entry state, and `MC_PRE_SPAWN_CLEAN_AWARD` for pre-award behavior. Read their return contracts before implementation; the local CallbackManager alias `postRoomClear` still maps to the pre-award callback.
- Key native-room state through `SaveManager.GetRoomSave(..., listIndex)` using the relevant `RoomDescriptor.ListIndex`; do not persist descriptor userdata or rely only on `Level:GetCurrentRoomIndex()`. StageAPI extra rooms are a separate identity domain: legacy version-9 Appraisal uses its floor token, fixed map dimension, stable room marker/`RoomID`, and entity `PersistentIndex`, not a native descriptor `ListIndex`. Choose normal versus `noHourglass` storage deliberately, and account for revisit, continue, Glowing Hourglass, and special rooms outside the native map.
- The base `MC_LEVEL_GENERATOR` callback is documented as inactive/broken and must not be used to build floors. Legacy version-9 Appraisal uses StageAPI `LevelMap`/`LevelRoom` extra rooms under `StageAPIGalleryRooms.MAP_DIMENSION`; that decision does not authorize the same backend, dimension, or persistence workaround for unrelated stages, vanilla room generation, monsters, or bosses.
- Legacy version-9 only: `StageAPIGalleryRooms.MAP_DIMENSION` is one project-owned fixed negative dimension. Never auto-allocate a different dimension or fall back to a native dimension. Before building or restoring, reject a foreign `StageAPI.LevelMaps[MAP_DIMENSION]` or foreign `StageAPI.LevelRooms[MAP_DIMENSION]` before payment, held-trinket mutation, or transition. Appraisal never reads, writes, places into, or transitions through native dimension 2/grid 80, never invokes `COLLECTIBLE_DEATH_CERTIFICATE`, and never blocks/cancels its use. Vanilla Death Certificate and Atropos therefore remain independent and may be used before or after Appraisal on the same floor.
- Legacy version-9 only: Appraisal's StageAPI backend currently registers one empty 1x1 layout and uses a bounded capacity of 28 stock pickups per room. Every new graph uses only that layout; the retired native 1x2/2x1/2x2 manifests are incompatible with session version 9 and are not silently migrated. Whenever at least three stock rooms are required, the first stock-room hub must have two distinct child branches before ordinary frontier growth. Reserve the entrance's LEFT0 for Appraisal's always-available per-visit return door. Stock positions keep dense adjacent-grid patterns, every possible door-aligned cross axis clear, and 180-degree pair ordering so a partially filled final room remains balanced. Do not add these runtime StageAPI layouts under `content/rooms` or vanilla stage resources.
- Legacy version-9 only: Every Appraisal virtual room has a unique stable marker separate from its reusable layout key. Persist only serializable fields such as the floor token, fixed map dimension, stable `RoomID`, map coordinates, room kind/layout identity, seeds, and stock assignments; never store `LevelMap`, `LevelRoom`, layout, entity, or other userdata. Rebuild only when the complete marker set validates, and do not treat `MapID`, array order, shape name, or an off-grid native descriptor as durable room identity.
- Legacy version-9 only: Installed StageAPI 2.33 clears `LevelRooms`, queues their normal reconstruction in `StageAPI.RoomsToLoad`, and loads `LevelMaps` first; a populated saved map calls `AddRoom(nil, ...)` before the referenced `LevelRoom.Shape` exists. Appraisal therefore must expose only an empty `Map = {}` shell for its fixed dimension to StageAPI's save data and persist the topology in its serializable manager graph plus each saved `LevelRoom` ownership marker. In `POST_STAGEAPI_LOAD_SAVE`, validate/adopt that exact empty shell, consume and remove every owned `RoomsToLoad` entry while reconstructing its `LevelRoom` from the provider's saved room data, validate the complete marker and actual `LevelRoom` payload (registered layout identity, shape/type, deterministic seeds, and extra-room flags), register it with `StageAPI.SetLevelRoom`, and only then repopulate the `LevelMap`; explicitly restore the provider-omitted `LevelMap.Persistent`, `LevelMap.OverlapDimension`, and each owned `LevelRoom.IsPersistentRoom`. Installed 2.33 also overwrites saved `LastPersistentIndex` while rebuilding an empty layout, so recompute it from reserved stock indices plus saved `PersistenceData`, `AvoidSpawning`, and `ExtraSpawn` before any new persistent entity can be assigned. A continued complete graph must fail closed when its shell or any saved room is missing, duplicate, foreign, or payload-incompatible; `rebind` must never replace missing provider state with fresh empty rooms. Never leave a validated owned queue entry for the later `MC_POST_NEW_LEVEL` drain to overwrite, never delete an ambiguous/foreign queue entry, never feed a partially reconstructed room set to `AddRoom`, and do not monkey-patch StageAPI.
- Legacy version-9 only: The Appraisal graph is built at most once per floor and reused for every paid visit on that floor. `MC_POST_NEW_LEVEL` must first durably settle any unresolved entry or pickup/Smelter journal without attempting to return to a destroyed origin. Floor cleanup must then remove every owned room from the map (or explicitly `StageAPI.SetLevelRoom(nil, roomID, MAP_DIMENSION)`), consume owned queued saves, clear owned `LevelRooms`, `RoomGrids`, `CustomGrids`, transition/current-map references, and owned MiniMAPI entries, call `LevelMap:Destroy()`, and immediately persist the provider cleanup with `StageAPI.SaveModData()` before clearing the manager session. `LevelMap:Destroy()` alone is insufficient because installed 2.33 does not remove associated level rooms. A saved graph or the fixed numeric dimension alone is not ownership evidence; never mark or delete a foreign provider map or MiniMAPI room after failed validation.
- Legacy version-9 only: StageAPI virtual rooms do not create native `RoomDescriptor`s and therefore cannot enter the engine's vanilla minimap graph or GoodTrip's native-room overlay. Appraisal uses the required MiniMAPI provider to display the complete graph in the normal minimap HUD area; this is provider integration, not a Conch-rendered replacement HUD. After every materialization or continue restore, validate that the fixed MiniMAPI level contains only project-prefixed entries or the exact numeric entries StageAPI just auto-created, clear those owned entries, then register every graph room exactly once with stable prefixed IDs, exact coordinates/shape/dimension, and `DisplayFlags = 5`. Reject a foreign entry before replacement, remove only owned entries during cleanup, and keep the rooms explicitly non-teleportable unless a separate transaction-safe MiniMAPI handler is deliberately implemented. Never add a custom HUD, monkey-patch GoodTrip, or claim native-minimap support.
- Appraisal freezes the sorted registry of every non-hidden trinket config once per floor and assigns it to fixed per-room slots. - Distinguish the child-devouring Titan Kronos (Cronus, Zeus's father) from Chronos (time). - Treat item icons as native 32x32 pixel art. If an AI or high-resolution draft is used, always finish with direct 32x32 cleanup; do not rely on automatic downscaling for final edges, layer order, or readability.
- When an art draft is approved, preserve its silhouette, proportions, palette and highlight placement during native-grid finishing. Final enlarged previews must be integer nearest-neighbor enlargements of the exact runtime PNG; clearly distinguish an unfinished generated concept from the asset being applied.
- For style references, prefer vanilla Isaac collectible sprites from `extracted_resources/resources/gfx/items/collectibles` and high-quality local mod references such as Epiphany, Astrobirth, and Auri only for general production traits. Do not copy, trace, or recreate another mod's specific item artwork.
- Match the common Isaac item language: compact readable silhouette, slightly handmade asymmetry, transparent corners, near-black 1-2 px outline, top-left lighting, muted grimy shadow colors, and small clusters of bright highlight pixels.
- Keep each material on a limited palette. A good default is outline, dark shadow, midtone, and one sparse highlight; use extra highlight colors only for the focal point.
- For small effect sprites, judge the native Isaac silhouette, flat color shapes, and overall mood at actual gameplay size before adding surface detail. Preserve the subject's identity and intended emotion while adopting Isaac's rendering language; do not transplant a recognizable vanilla enemy's anatomy as a substitute for reinterpretation. Dense teeth, texture, or high-resolution detail do not substitute for matching that visual language.
- Avoid muddy antialiasing, soft gradients, airbrushed glow, photorealistic detail, and thin hairline elements that disappear at 32px. Favor hard pixel clusters and clear shape separation.
- Check layer order manually after scaling or cleanup. Foreground tools, blades, handles, knots, and cut points should visibly overlap in the intended order at 32px.
- For AI sprite prompts, specify final native 32x32 readability, hard pixel edges, limited palette, transparent padding, no text/UI/frame/pedestal, and "reference style traits only, no copying" when using vanilla or mod art as inspiration.

## Callback Guidelines

- Avoid adding `MC_POST_UPDATE`, `MC_POST_RENDER`, `MC_POST_PEFFECT_UPDATE`, or broad entity callbacks unless the item needs them continuously.
- If a broad callback is necessary, return early before expensive work. Check ownership, subtype, variant, or custom `GetData()` flags first.
- For item behavior, prefer `ItemData.callbacks` plus `CallbackManager` over scattered direct `AddCallback` calls.
- `scripts/callback_manager.lua` is an ItemData registrar, not a generic entity/room callback framework: it iterates only `ConchBlessing.ItemData`, registers after the item loader has loaded every behavior module (with `MC_POST_GAME_STARTED` retained only as an idempotent fallback), and only auto-filters familiar variants. Do not route a new entity or room subsystem through it without redesigning and verifying those semantics.
- CallbackManager keys are conveniences, not API contracts. Confirm the mapped `ModCallbacks` value, supported filter parameter, callback phase, arguments, and return behavior in both `callback_manager.lua` and the current docs before implementing a callback.
- The vendored IsaacScript Common root does not re-export `CallbackPriority`; `isc.CallbackPriority` is `nil` even though the vendor uses that enum internally. For direct `AddPriorityCallback` registrations, resolve the engine/REPENTOGON global `CallbackPriority` and use the documented `EARLY`/`LATE` values with a local numeric fallback. A room/entity loader is wrapped by core `pcall`, so an initialization error can leave a partially populated global namespace; capability flags must be assigned only after all required callbacks register, and `ConchBlessing.printError` must mirror failures to `Isaac.DebugString` so the runtime log exposes the original load error.
- Do not use the legacy ItemData `pickup` key as a collectible-acquisition event. It maps to `MC_POST_PICKUP_INIT`, whose callback entity and variant filter do not represent the player acquiring the collectible; use a documented add/remove-collectible callback with its exact signature or a cache-owned state transition instead.
- Match documented callback argument order exactly. Never hide a shifted or missing player argument by falling back to `Isaac.GetPlayer(0)`; reject invalid callback input and preserve the actual triggering player in multiplayer. ItemData handlers are registered with `ConchBlessing:AddCallback`, so like any `Mod:AddCallback` handler they receive the mod first: a `use` handler is `(_, id, rng, player, flags, slot, varData)` (Power Training and Inf D6 once took `player` first and always acted on player 0).
- Do not register empty callbacks through `ItemData.callbacks`.
- Cache static `ItemConfig` scans and repeated ID lists. Do not scan `CollectibleType.NUM_COLLECTIBLES` every frame.
- Avoid repeated `Isaac.GetRoomEntities()` or `Isaac.FindByType()` in per-entity update callbacks. Cache per-frame data or store runtime references when safe.
- Preserve multiplayer behavior by iterating `Game():GetNumPlayers()` when the effect can belong to any player.
- For attack-count thresholds, never group projectile callbacks by game frame. Reuse `scripts/lib/weapon_attack_tracker.lua` with the engine's semantic attack event. Breath uses REPENTOGON `MC_POST_TRIGGER_WEAPON_FIRED`: advance once per callback, never by `FireAmount` or `Weapon:GetNumFired`, and attribute only a direct `EntityPlayer` weapon owner. Multishot and familiar-owned mirror weapons must not add counts, while item-spawned secondary entities must not re-enter the counter. The base API has no exact fallback, and familiar-only weapon attacks have no shared player-action token; keep those dependency and scope limits explicit rather than restoring frame inference or item/familiar special cases.
- Eye-specific attack restrictions concern the attack's originating eye, not its travel direction or screen position. Establish provenance for each supported weapon and its derived attacks; a player's current alternating-eye value after firing is not proof of every spawned attack's origin. Do not equate moving shots to the right, reducing global tears, or removing an existing projectile with cancelling a left-eye attack before firing. Keep unsupported weapon paths and unfinished restrictions explicit in tests and descriptions.
- Prefer semantic callbacks and explicit state transitions over frame numbers or fixed frame delays. Do not infer game initialization, pickup completion, room readiness, or session phase from `Game():GetFrameCount()` when an ownership, pickup, room, entity, or queue event can establish it directly.
- `MC_POST_NEW_ROOM` and `MC_POST_NEW_LEVEL` can run before `MC_POST_GAME_STARTED` while SaveManager still exposes the previous on-disk run table. A room subsystem with run-scoped journals must keep an explicit lifecycle gate closed until its own game-start reconciliation finishes, close it on `MC_PRE_GAME_EXIT`, and make pre-start room/level/update/acquisition callbacks no-ops; never infer readiness from frame count.
- If a frame delay is unavoidable because the engine exposes no readiness event, document the reason, bound the wait, and clear pending state when a game or room transition invalidates that work.

## Damage Triggers And Provenance

- A collision callback proves contact, not applied HP damage. Base `MC_ENTITY_TAKE_DMG` runs before damage and may still be cancelled or changed; when a proc contract requires damage that actually occurred, use REPENTOGON `MC_POST_ENTITY_TAKE_DMG` or make the weaker fallback and its limitation explicit.
- Classify damage by its actual attack entity, not by an adjacent effect or a negative list of known attacks. For REPENTOGON post-damage callbacks, inspect `ExtraSource.Entity` first and fall back to `Source.Entity`; `ExtraSource` preserves laser, knife, and other hitbox provenance that the normal source may collapse to a player.
- Existing engine `DamageFlag` values may be bitwise-ORed and passed when code directly invokes a damage API such as `Entity:TakeDamage`, `Game:BombDamage`, or `Game:BombExplosionEffects`. Native spawned attacks normally receive their damage flags from the engine; do not assume an entity's `Flags` field contains `DamageFlag` values (`EntityBomb.Flags`, for example, contains `TearFlags`).
- There is no `DAMAGE_TEAR` and no safe project-owned `DamageFlag` or `TearFlags` bit allocation. Reuse `DamageProvenance.getEligiblePlayerAttack(source, extraSource, procKey)` instead of classifying attacks by flags or entity-type lists. When ownership and a discrete attack identity can be established, hit-triggered effects accept every player-owned damage source, including direct weapons, familiar-fired attacks, and attacks created by other items; fail closed when no player owner, actual source, or semantic attack boundary can be resolved.
- Prevent recursion with per-proc causal lineage, not a global attack-type or secondary-attack ban. Give each hit proc a stable key, carry the incoming provenance snapshot into its output through `markTriggeredAttack`, and accumulate that key in the lineage. A consumer rejects only a lineage that already contains its own key: the same laser, void, explosion, or other attack form from an unrelated source remains eligible, each distinct proc key may enter a causal branch once, and cycles terminate when a key would repeat.
- Treat recursion lineage and repeated-hit consumption as separate state. For a chance proc that should roll once per physical attack, call `DamageProvenance.tryClaimAttackProc(attackEntity, procKey)` after confirmed-damage, target, ownership, and item checks but before RNG; a failed roll still consumes that attack's opportunity. Claims are per exact attack entity and proc key, are not inherited through `procChain`, and must never be keyed by frame, damage cooldown, or target. A piercing tear, bomb explosion, Tech X ring, or Brimstone beam therefore rolls each proc once across all of its hits and targets, while distinct multishot entities remain distinct attacks.
- When the engine reuses a melee weapon's main `EntityKnife` across attacks, start a fresh claim state only from the semantic REPENTOGON `MC_POST_TRIGGER_WEAPON_FIRED` event and capability-checked `Weapon:GetMainEntity`, after its player ownership matches the callback owner; do not infer a reset from animation frames or elapsed time. Do not apply this generic reset to fresh or still-live tears, bombs, effects, or lasers: their exact entity is already the attack identity, and resetting an active laser can reopen an older Tech X ring or continuous beam. Canonicalize REPENTOGON melee hitboxes through `EntityKnife:GetHitboxParentKnife` for both claims and lineage resolution. Any other reused entity needs an exact producer callback/token with a documented lifecycle or must fail closed. A familiar body is a long-lived owner/contact hitbox, not a discrete attack, unless an exact producer explicitly opens its attack state. Do not treat `EntityFlag.FLAG_THROWN` as a throw-lifetime token or assume attack damage occurs synchronously between semantic pre/post callbacks unless the target runtime/source proves those contracts. If the engine exposes only a bare player/source, a source-less status tick, or another long-lived contact entity with no semantic attack boundary, use an explicit producer-scoped attack state or fail closed rather than permanently claiming the owner or inventing an attack token.
- Preserve lineage across delayed work by storing the plain provenance snapshot in the pending runtime record, and use `withTriggeredSource` around synchronous direct-damage APIs whose `Source` collapses to a player. Mark outputs at their semantic spawn/damage call, then let the shared tear, bomb, laser, knife, effect, projectile, familiar, and split-child inheritance callbacks propagate the lineage. Do not add item-name exclusions to consumers.
- Some engine-owned delayed damage, such as a status tick, may discard the applying attack and player from both `Source` and `ExtraSource`. Do not recover ownership from `DamageFlags`, a recent-hit/frame association, or the nearest player; fail closed unless a semantic source or a producer-carried provenance snapshot is available.
- When both an applied-damage callback and a base collision fallback are registered, the fallback must return before dedupe, lockout, RNG, or other state changes whenever `MC_POST_ENTITY_TAKE_DMG` is available. The fallback must also reject proc-ineligible provenance; its collision-only limitation remains part of the REPENTOGON-recommended compatibility path.

## Save Data

- Use `ConchBlessing.SaveManager` for persistent and run-scoped state.
- When a system grants ordinary collectible copies that must later be removed while identical player-owned copies may coexist, inventory totals are not ownership. Persist the active system-owned contribution and the player's pre-grant baseline, update them together, and remove only copies above that baseline. If a cap means “ever during this ownership” rather than “currently active,” persist that lifetime total separately. Kronos familiar conversions use `itemGrants`, `itemGrantBaselines`, and `itemGrantTotals` for these roles. Several familiars may convert into the same collectible, so grants and lifetime totals stay per familiar (`fam_<id>`) while the baseline belongs to the granted item (`item_<id>`); a lost copy is charged to exactly one familiar, and a legacy `fam_<id>` baseline is adopted as the item baseline. A mapping that stops granting its item moves to Kronos `RETIRED_GRANTS`, whose migration removes the old grant above the baseline before anything infers a baseline from the item count. Copies a GB Bug hands back are recorded in `spared` and stay exempt from re-absorption only while the player still owns them; Buddy in a Box / Lil Delirium picks live in `floorPicks`, keyed by the run-save `floorSerial` that advances on each gated `MC_POST_NEW_LEVEL`, and only raise effect counts (`_getEffectCount`), never grants or pinned familiars. Familiars that do not come from an owned collectible are absorbed only from an allow-list of sources (Box of Friends, Monster Manual, The Twins, Soul of Lilith, the Pretty Fly pill under REPENTOGON, Sacrificial Altar): the source's familiar-type collectible effects are read from and removed out of the player's `TemporaryEffects`, room credit stays runtime, Monster Manual use evidence is captured before/after the active even without Kronos and stored in the triggering player's floor save; consumed source counts prevent replay rewards, while active credit and its conversion-grant contribution live in `tempFloor` keyed by `floorSerial`. Its floor expiry removes only its own converted copies above the shared item baseline. Soul of Lilith credit lives in `tempPermanent`, and absorbed pill flies in `prettyFlies`; losing Kronos re-adds those effects and flies. Wisps, blue flies/spiders, locusts, and short card/trinket summons keep their vanilla behaviour, and so do Tonsil (the engine keeps its count in a player field with no API, so a removed Tonsil is respawned) and Found Soul (a ghost player, not a familiar).
- Choose the narrowest matching scope: `GetRunSave`, `GetFloorSave`, `GetRoomSave`, or `GetTempSave`. Pass the actual player/entity when state has an owner, and use `noHourglass` only when reversal is intentionally suppressed.
- Per-player state belongs to that player, never to a `GetPlayerType()` or `ControllerIndex` key: same-character co-op players, Jacob & Esau, Strawman and a player added mid-run share those, and a character change (Lazarus's revive, Clicker) moves a type key away from its owner (audit 2026-10-23). Saved state goes in `GetRunSave(player)` / `GetFloorSave(player)`, which SaveManager keys by the player's collectible-RNG seed: it survives Continue, follows a character change, and is deleted when that player entity is removed. Process-local caches key by `GetPtrHash(player)` and reset at game start. Migrate an older type- or controller-keyed record once to its matching player and drop the old key. Live Eye's multiplier (`liveEye`) and Utility Belt's marks (`utilityBelt`) are such run-save state, so Continue keeps them.
- A dead player or co-op ghost does not act for its items: 진's strikes and twisters, Eternal Flame's removal and payout, and Tyrfing / Sealed Demon Sword kill credit and splits skip them (`IsDead`, capability-checked `IsCoopGhost`); 진's weather stays while anyone holds it. EID live values describe `EID:ClosestPlayerTo` (capability-checked), not player 0.
- Use `GetPersistentSave` for non-setting data that must survive across runs, such as project-managed unlock state, and `GetSettingsSave` for configuration. These file scopes do not have matching `TryGet*` forms; consult the vendored annotations instead of inferring one.
- In multiplayer, bind state to the callback's triggering player or SaveManager's entity-scoped save. Do not use player 0 or a module-global table as a substitute for ownership unless the design is explicitly shared across all players.
- Store persistent MCM/settings data under `SaveManager.GetSettingsSave().config` through the existing config helpers.
- Store serializable data only. Do not write entity, sprite, font, RNG, or userdata objects into saved tables.
- If runtime entity references are cached, clear them on room/game transitions and keep them out of SaveManager data.
- Kronos bulk release restores the exact collectible/effect inventory and withdraws owned contributions in the same gameplay transaction. Cosmetic work must be bounded independently of copy count: combine duplicate release icons, cap representative types and dust draws, and discard that player's obsolete absorption queue on final loss. Never delay or truncate gameplay returns to meet a visual budget, persist a visual queue, or clear another player's effects.
- The gallery manager owns the shared `GetRunSave(nil, false).appraisalGallerySession` record. Its frozen catalog, floor identity, serializable backend-specific room manifests, per-room `closedRooms`, stock source assignments, visit/acquisition journals, and version-9-only tagged Atropos Death Certificate detour form a floor-scoped ledger even though the physical table is run save. Every same-floor normal return, unexpected extra-room exit, recovery escape, continue, repeated use, and active DC detour must preserve the ledger as a completed tombstone. A genuinely different floor resets it only after any unresolved entry/acquisition journal has reached a durable cross-floor settlement tombstone; never erase an applied reward journal merely because `MC_POST_NEW_LEVEL` fired. Per-visit origin, owner, payment, pending reward, and transition fields reset for each paid entry. Keep only serializable floor/map/room markers, exact held IDs, plain smelt-count baselines/deltas, commit progress, phase, and transition metadata there; never store StageAPI objects or native descriptor userdata.
- Legacy version-9 only: StageAPI's own map save record for `StageAPIGalleryRooms.MAP_DIMENSION` is deliberately an empty LevelMap shell; its separate saved LevelRoom records may still appear in `StageAPI.RoomsToLoad`. Conch Blessing's saved graph plus the complete LevelRoom marker set are jointly authoritative: `POST_STAGEAPI_LOAD_SAVE` consumes/removes the owned queued room saves, reconstructs/registers and validates every marked `LevelRoom` before repopulating the shell, rebinds stock by `PersistentIndex`, and restores `LevelMap.Persistent`, `LevelMap.OverlapDimension`, and each owned `LevelRoom.IsPersistentRoom`. Missing continued provider state fails closed and must not be regenerated as an empty room. On a real floor change, settle the transaction journal first, then explicitly remove the owned rooms, queues, and dimension-scoped provider/MiniMAPI state before `LevelMap:Destroy`, immediately call `StageAPI.SaveModData()`, and only then clear the manager session. Do not leave owned entries for StageAPI 2.33's later queue drain, treat a graph alone as map ownership, or rely on `Destroy()` alone.
- Atropos owns `atroposNativeDeathCertificate` for its native-dimension session/choice ledger and `atroposChoiceOptionGroups` for temporary option-link ownership. The latter stores only room identity and pickup `InitSeed` to original nonzero `OptionsPickupIndex` mappings; remove a room's mappings when the last owner restores/relinquishes them so stale records cannot overwrite another provider.
- A call to vendored `SaveManager.Save()` returning without an exception is not proof of persistence: that implementation silently returns on initialization, copy, backup, or JSON-validation failures. Write-ahead gameplay transactions must observe the matching `POST_DATA_SAVE` completion callback before performing their irreversible step. After `SaveManager.Init`, public `SaveManager.SaveCallbacks.*` values already include the mod-specific prefix; register those IDs directly on `ConchBlessing.originalMod` and do not prepend `__SAVEMANAGER_UNIQUE_KEY` again. Like every callback registered through `Mod:AddCallback`, a SaveManager callback receives the registered mod as its first argument: `PRE_DATA_SAVE` handlers that use or return the payload must use `function(_, saveData)`, never mistake the mod object for serializable data.
- Once a transaction is committed, never infer that it rolled back solely because a later inventory or currency total equals a pre-transaction value; unrelated gains and spending can collide with that total. Revalidate a provider-owned semantic delta when one exists, otherwise trust the committed journal or fail closed without mutating unrelated state.
- Never reopen manager-owned stock after a failed automatic grant unless the exact transaction-owned inventory delta was removed, the complete post-rollback inventory snapshot exactly matches the prepared baseline, and a semantic rollback-complete state was durably saved. Persist cancellation-complete and rollback-complete phases before clearing their journals so a failed cleanup save or continue can finish safely. If rollback or every save barrier fails, retain the pending journal and route the session to recovery so the same stock cannot grant twice.
- SaveManager journal data and the engine's player inventory are separate persistence stores, so a hard process crash between their writes cannot be made truly atomic by Lua. Use prepared/complete phases and exact snapshots to fail closed, then cover quit/continue at each transaction boundary in the in-game verification matrix; do not invent frame-based reconciliation or guess ownership from coincidental totals.

## Commit And Changelog Style

- Follow `https://git.intp.me/` for commit messages: `Type: English title` on the first line, one blank line, then Korean `- ` bullet body lines.
- Commit titles must use one of the allowed capitalized types from the guideline, keep the English title near 25-30 characters, and omit a trailing period.
- Commit body bullets must explain what and why in Korean, start with `- `, avoid blank lines between bullets, and end with a noun-style phrase such as `추가`, `수정`, `제거`, `전환`, `적용`, or `정리`.
- Before any `dev` to `main` merge, push, or release-version decision, run `git fetch origin` and compare against `origin/main` and `origin/dev`. Do not decide from stale local branch state.
- Do not change `metadata.xml` versions during `dev` to `main` merges, release-merge requests, pushes, or ordinary dev commits unless the user explicitly requests a version change.
- When preparing a `dev` to `main` merge, compare `metadata.xml` versions on fetched `origin/main`, `origin/dev`, and the branch being merged. Do not manually bump versions for the merge; let the Steam publish workflow resolve the publish version unless the user explicitly requests a specific version change.
- The Steam publish workflow has an optional manual `version` input. A manual `version` greater than the downloaded Steam Workshop version is used as the publish version, even when it differs from committed `metadata.xml`.
- If a manual workflow `version` is equal to or lower than the downloaded Steam Workshop version, ignore that input and use the empty-version automatic resolution path.
- With empty `version`, the Steam publish workflow downloads the current Steam Workshop item, compares its `metadata.xml` version with the committed version, and stages the committed version only when the committed version is greater than the Workshop version.
- With empty `version`, if committed `metadata.xml` is equal to or lower than the downloaded Steam Workshop version, stage and upload the next patch version after the downloaded Workshop version.
- The Steam publish workflow may edit `metadata.xml` in the workflow workspace before staging the upload package, but it must commit and push that resolved version only after SteamCMD upload succeeds.
- Steam Workshop changenotes should match the existing workshop style: one or more English typed summary lines such as `Fix: Fix EID Bug`, then a blank line, then short Korean summary lines without `-` bullets.
