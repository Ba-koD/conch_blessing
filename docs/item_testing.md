# 아이템 자동 테스트

게임 내 콘솔에서 Lua 수정본을 불러온 뒤 실행한다.

```text
luamod conch_blessing
conch_test
```

`conch_test`는 상태를 원복할 수 있는 검사를 먼저 묶고, 나머지 ItemData 항목은 이름순으로 실행한다. 현재 43개 항목 중
32개가 구현되어 있고, XML 생성에서 제외된 개발 중 항목 11개는 `SKIP`이다.
크로노스·라이브 아이·감정평가서는 기존 상세 벤치까지 별도의 새 런에서 실행한다.
생명주기·기존 상세 검사 46개에 조건·시너지·피해 시나리오를 연결하여,
중복을 제거한 전체 실행은 현재 **105개 벤치**다. 크로노스 공통 계약 80개는 기존 3개 묶음으로, 추가 능력 30개는 3개 순차 묶음으로 실행한다. 벨트 제외 액티브 7개도 한 런으로 묶었다. 이전 전체 실행의 138개에서 33개를 줄인 수치이며 검사 대상은 유지한다. 안전하게 정리된 검사끼리는 같은 런을 공유한다. 마지막 검사가 기준 상태로 복원되면 종료 시에도 런을 유지하며, 다음 개별 명령에서 다시 검증해 재사용한다. 재시작이 필요하면 로그에 `RESET reason`을 남긴다.
수 분 이상 걸릴 수 있으므로 테스트 런에서 실행하고, 콘솔을 닫고 기다린다.
최초 검사는 **싱글 플레이 아이작** 테스트 런으로 시작하며, 이후에는 정리가 검증된 호환 검사끼리 이어서 실행한다.

MCM 디버그 ON/OFF에 관계없이 START/PASS/FAIL/SKIP/END와 기대값·실제값을 콘솔과 로그에 모두 기록한다.
결과는 `log.txt`의 `[ConchTest]`, `[ItemTest:키]`, 상세 Probe에 남는다.
검사 중 화면 하단 중앙에 `1/105 Test - conch_test ...` 형태의 진행 번호·명령,
현재 검사 구간·단계·대기 틱과 PASS/FAIL/SKIP 수가 표시된다. 개별 실행은 `1/1`로 표시되며,
재시작·정리 중에도 표시를 유지하고 종료 후 사라진다. MCM 디버그 설정과 무관하게 표시된다.
방 이름과 겹치지 않도록 아래쪽에 배치하고 검은 외곽선을 적용한다. 긴 문구는 화면 폭에 맞춰 줄바꿈한다.
화면을 지켜보며 확인 버튼을 누를 필요는 없다. 공통 시나리오의 20틱 준비 대기를
플레이어·저장 데이터 준비 확인으로 바꾸고, 이전 탄환이 사라지기를 기다리지 않고 격리한다.
실제 공격·사망·흡수·액티브 사용 결과를 확인하면 다음 검사로 이동한다.
SOFLAM 지연·상태 이상 지속 시간과 기존 상세 벤치의 캡션 렌더 검사는 실제 대기를 유지한다.
표적은 접촉 피해가 없고 사망 후 다른 적을 만들지 않는 파리이며, 지상 장판에는 Maggot을 사용한다.
사망 검사는 첫 NPC 업데이트와 취약 상태를 확인한 뒤 실제 치명타 피해를 주며,
피해 수락·HP·kill 이벤트·remove 이벤트와 `MC_POST_NPC_DEATH` 완료를 구분한다.
즉시 소멸하는 적은 같은 방의 같은 개체(포인터+생성 시드)에 대한 치명타 수락과 kill+remove가 모두 있어야 처치를 인정한다.
사망 완료 콜백 횟수는 별도로 기록하고, 처치 확인 뒤 실제 보상·누적 수치도 반드시 검사한다.
방 전환에 의한 제거, 다른 개체에 복사된 표식, 거부된 피해는 처치 성공으로 바꾸지 않는다.
동결·타깃 제외 플래그로 상태 이상·사망·오라 검사를 가리지 않는다.
예상하지 않은 플레이어 사망은 `FAIL`로 기록하고, 업데이트가 멈춘 게임 오버 화면에서도
다음 벤치로 재시작한다. 1UP 부활을 의도한 검사는 최대 300 렌더 프레임만 기다린다.
플레이어 제거/실종은 사망과 다른 FAIL로 기록한다. 플레이어가 사라져 업데이트가 멈춘 경우에도
렌더 콜백에서 제한된 시간 후 정리하여 무한 대기를 막는다.

첫 목록은 검토한 2026-10-09 전체 실행의 28개 FAIL을 **13개 시나리오**로 묶은 것이다.
Lua가 운영체제의 `log.txt`를 읽는 방식은 아니다. 이후 실행 결과는 개발용 영구 저장 영역에 기록하며,
완주하고 FAIL/SKIP이 없는 시나리오만 목록에서 제거한다. 중단·미실행·SKIP은 통과로 처리하지 않는다.
관련 없는 개별 테스트를 통과해도 다른 실패는 남고, 새 실패는 추가된다.
저장은 SaveManager의 실제 쓰기 완료 콜백으로 확인하며, 실패하면 로그에 ERROR를 남기고 메모리 목록을 보존한다.
목록이 비면 안내만 하고 재시작하지 않는다. `latest list`도 재시작하지 않는다.

피해 검사에는 정확히 선택한 공격의 명중 횟수·피해량·불꽃 나이·남은 수명·빙결 잔여 시간을 남긴다.
얼음 브레스에는 기본 파란 불꽃의 0/5/10틱 변화와 `AddFreeze(60)` 1회/반복 적용 대조도 추가했다.
대조 측정은 `DIAG`이며 아이템 통과 수를 늘리지 않는다.
파란 불꽃의 피해 기대값은 기본 계수(공격력 × 0.2 × 보유 수)에 명중 시 수명 감쇠를 곱한다.
2026-10-09 22:32 원본 로그의 15개 명중은 `남은 수명 / (남은 수명 + 나이 - 1)`에 모두 일치했다.
이것은 관측으로 도출한 엔진 계산 가설이므로 매 실행 시 서로 다른 나이의 표식 없는 바닐라 파란 불꽃으로
실제 HP 감소를 먼저 대조한다. 대조군이 계산과 다르면 종속 아이템 검사를 중단하고 실패 원인을 남긴다.
아이템의 기본 계수·발사 간격·탄 수·중첩 기대값은 그대로 독립 검사하며, 측정 피해를 기대값으로 역산하지 않는다.
피해·상태 이상 검사는 첫 적용 명중에서 공격을 제거해 재충돌을 막는다. HP 버퍼 반영을 기다린 후
명중 1회 및 외부 공격 혼입 0회를 요구한다. HP 오차는 float32 정밀도 기준으로 제한하며,
빙결은 실제 1회 명중에 대한 기존 60틱 기대값을 유지한다.
꼬인 한 쌍 등 앵커는 `FindByType`에서 제외되는 `FLAG_NO_QUERY` 개체도 포함하는 전체 방 목록으로 검사한다.
소유자·생존·표식을 확인하고, 내부 추적 배열만 남은 경우에는 통과시키지 않는다.
정리 검사는 정상적으로 원복되면 즉시 진행하고, 잔여 효과가 있으면 최대 120업데이트 동안 자연 소멸을 관찰한다.
검사를 통과시키려고 반복 삭제하지 않는다. 소멸하지 않으면 해당 엔티티의 나이·피해량과 함께 실패한다.
이전 묶음 중단으로 `NOT RUN`이었던 9개는 실패 재검사 목록에 넣지 않았다. 이들의 검증은 별도로 남아 있다.

`conch_test atropos death_certificate`는 선택한 아이템이 획득 대기열에 들어간 즉시 받침대가 지워지는지 먼저 확인한다.
그 뒤 획득 완료 후 같은 방·차원에 남고 귀환 전환도 시작되지 않았는지,
선택한 아이템을 정확히 하나 얻고 그 방의 나머지 받침대는 사라졌는지 따로 검사한다.
다른 방을 먼저 방문해 진열 상태를 기록한 뒤 선택 후에도 그대로인지 비교하며,
선택을 마친 방의 재방문에서도 빈 상태를 확인한다. DC 진입 후 아트로포스를 얻어도 문이 생기고 카드가 늘지 않는지, 마지막 장신구를 제거한 후에도 문으로 원래 방에 돌아오는지 검사한다.
이 보강 검사는 게임 재실행 전에는 구현된 검사일 뿐 실행 통과로 취급하지 않는다.

상세 검사도 `conch_test kronos detail`, `conch_test live_eye detail`, `conch_test appraisal detail`로 실행한다.
캡션 미리보기는 `conch_test kronos detail caption`이다. 이전 별도 접두사 명령은 등록하지 않는다.
텍스트·통계 분포·반올림 도구는 아이템 생명주기 전체 실행에 포함하지 않는다.

계속 남는 효과·기록·대기 작업은 FAIL/RESET이며, 상태가 불분명한 항목도 자동으로 PASS하지 않는다.

같은 런을 공유하는 대상은 크로노스의 일반 능력·공격·오라·차단·벨트 묶음과 생명주기,

크로노스와 벨트는 각 호환 그룹 안에서 묶음 사이뿐 아니라 개별 명령 사이에도 런을 유지한다.
검사 후 인벤토리·활성 슬롯/충전·6개 스탯·체력/자원·엔티티·아이템 저장 상태·StatsAPI 기여량·획득 대기열·층 피격 상태를 확인한다.
동작 검사 FAIL과 정리 FAIL을 구별한다. 동작이 실패했더라도 별도로 복원을 확인하면 이어서 검사한다.
정리 실패·취소·기준 상태 변경·그룹 불일치 때는 이유를 남기고 재시작한다. 영구 보상·시간 누적·배열 소모·새 층·그리드 변동처럼 원복을 증명할 수 없는 경우는 별도 런이다.
크로노스 정리는 본체 제거→반환 업데이트→반환 펫 제거→업데이트 순서로 검사하며, 저장 효과·임시 능력·대기 콜백까지 확인한다. 저장값을 강제로 비워 통과시키지 않는다.

아트로포스에는 추가 순환 선택지 +1 효과가 없으며, 해당 문구는 한국어·영어 설명에서 삭제했다.
추가 순환 선택지는 적사단지의 보유 효과다. 일반 적사단지는 +1, **황금 강화된 적사단지 자체를 보유하면 +2**이며 기존 배열에 더한다. 바닥 아이템의 황금 여부는 무관하다. 설치된 Golden Items 1.1은 액티브의 자연 황금화를 막으므로 공개 API로 강화된 상태를 검사한다. 슬롯별 황금 액티브를 지원하는 Epiphany가 활성화되면 그 공개 API를 우선한다. 외부 모드는 수정하지 않았다. 새 게임 검사는 구현 완료 / 실행 대기 상태다. `tests/test_severed_oath.py`의 저장 재구성 검사는 Lua 회귀검사이며 실제 Continue 성공을 의미하지 않는다.

## 검사 내용

추가 시나리오 전체 표는 [시너지·조건·피해 검사표](synergy_testing.md)에 있다.
**코드 작성·오프라인 검증 완료, 새 게임 실행 결과는 대기 중**이다.
144개 시너지의 등록 누락을 자동 검출한다. 목록 연결은 실행 성공을 의미하지 않는다.
실제 적 HP가 반영되는 다음 업데이트까지 기다려 최초 유발 피해와 추가 피해를 분리한다.
범위/단일 타격 검사는 실제 생성된 공격 하나만 남기고 표적을 배치하며, 공격의 피해량이나
수명을 바꾸지 않는다. 방 보상은 실제 적 사망에 의한 클리어와 엔진의 보상 API를 모두
거친다. 아이템 콜백 뒤·바닐라 보상 생성 전의 관찰 경계에서 모드가 만든 픽업을 센다.
추가된 개별 시나리오는 `conch_test <키> list`에 출력된다.
아이템 이름만 입력하면 전체 아이템 검사를, 뒤에 시나리오를 붙이면 그 검사만 실행한다.
잘못된 시나리오나 불필요한 인수는 오류 안내만 표시하며 런을 재시작하지 않는다.
로그는 사용자가 완료를 알린 뒤 확인한다. 자동 주기 감시는 중단되어 있다.

기본 순서는 **1개 획득 → 2개 중첩 → 1개 제거 → 전부 제거 → 재획득 → 다시 전부 제거**다.
패시브·패밀리어는 실제 수집품, 액티브는 스쿨백의 두 슬롯,
장신구는 엄마의 지갑으로 일반·황금 장신구를 각각 보유한다.
게임의 실제 추가/제거 API를 사용하고, 콜백이 반응할 시간을 준 뒤 검증한다.
아이템 제거 직후 테스트 코드가 캐시를 강제 갱신해서 제거 버그를 숨기지 않는다.
일시적 스탯은 전부 제거했을 때 기준값으로 돌아오는지 확인하고,
동일한 캐시를 세 번 평가해 값이 누적되지 않는지도 검사한다.

유도하지 않고 테스트 아이템을 계속 보유한 채 공격력·연사·사거리·행운·이동속도·탄속을

없는 상태에서 바닐라 입력 변화와 원복을 먼저 검증한다. 공격력은 공허의 단검의
10 데미지 지속시간 경계도 넘는다. 로그에 여섯 실제 수치와 각 실패의 기대값/실제값을 남긴다.

확률 함수에 통제된 난수를 넣는 검사는 `formula only`로 표시한다. 이것만으로
게임의 실제 발동 확률·분포를 검증했다고 하지 않는다. 생성 엔티티의 피해 속성 검사는
실제 적 HP 감소 검사와 구분하며, 장판 틱·모든 상태 이상·모든 시너지까지 통과했다는 뜻이 아니다.
새 검사들은 구현·오프라인 회귀 검증 상태이고 실제 게임 재실행 결과가 추가로 필요하다.
과거 중단 실행과 가장 최근 전체 END를 구분한다. 최근 전체 END는 2059 PASS / 47 FAIL / 11 SKIP이며, 실패 분석 후 수정한 코드의 게임 결과가 아니다. 그보다 오래된 1945 PASS / 100 FAIL / 11 SKIP 실행과 합산하지 않는다.

## 의도 기반 전체 검사 계획

아래 표는 **추가 구현까지 포함한 전체 계획**이다. 위의 현재 구현 표와 구분한다.
테스트 작성·정적 검사 통과·실제 게임 통과는 서로 다른 상태다. 현재 전체 게임 실행은
검증되지 않았다. 불꽃의 영구 보상과 마검의 전부 진화는 확정된 의도대로 구현했고,
해당 기대값을 유지한 채 실제 게임 재실행 결과를 기다린다.

기대 결과의 우선순위는 사용자 결정, 권위 있는 설명, 별도로 계산한 명세다.
프로덕션의 함수나 저장값으로 기대값까지 계산하여 같은 버그를 양쪽에 복제하지 않는다.
불명확한 동작은 확인한 뒤 확정한다. 내부 카운터는 진단 보조 수단이며,
적 HP 감소·지급물·플레이어 수치·이동한 방을 실제 결과로 판정한다.

## 결과 확인

`log.txt`의 `[ConchTest]`, `[ItemTest:<키>]`와 해당 상세 벤치 태그를 읽는다.
각 검사에 `PASS`, `FAIL`, `SKIP`이 찍히고, 마지막 `conch_test END`는 전체 합계를 표시한다.
필요 API가 없으면 해당 검사만 `SKIP`이며, 성공으로 계산하지 않는다.
로드 실패·예외·전환 시간 초과는 `FAIL`이며 해당 벤치의 후속 동작을 중단하고
깨끗한 런에서 다음 벤치를 실행한다. `FAIL` 벤치는 뒤의 검사까지 완료했다는 뜻이 아니다.
취소한 실행은 남은 벤치를 실행하지 않았다고 명시한다.


## 실행기 검증과 확장

```text
python -m unittest discover -s tests -v
```

Python의 `lupa`가 필요하다. 이 검사는 Lua 5.3에서 실제 실행기 코드를 불러
재시작 격리, 합산, 실패 전파, 시간 초과, 취소, 중복 등록, 전체 레지스트리 커버리지를 검사한다.
Isaac 엔진 검증을 대신하지 않는다.

새 아이템은 ItemData에서 명령이 자동 생성된다. 구현 항목에는
`item_test_stats.lua`, `item_test_combat.lua`, `item_test_special.lua` 중 하나에
실제 동작 계약을 추가해야 한다. 누락은 통과나 SKIP이 아니라 `FAIL`이다.
영구 효과는 `permanent`로 표시하고 그 유지·회수 규칙을 직접 검사한다.
테스트는 프로덕션의 결과를 미리 써 넣거나 아이템 콜백을 직접 호출해서 통과시키지 않는다.
